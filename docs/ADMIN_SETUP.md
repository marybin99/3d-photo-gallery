# 운영자 계정과 작품 관리 연결

관리자 주소는 **사이트 주소 뒤에 `/#/admin`**입니다. 예를 들어 로컬 서버가 `http://localhost:5174`이면 `http://localhost:5174/#/admin`으로 접속합니다. 작품 관리는 `/#/admin/artworks`, 방명록 관리는 `/#/admin/guestbook` 주소로 직접 접속할 수 있습니다. 기존 `/#/admin` 주소는 작품 관리를 표시합니다. 메뉴 이동은 URL에 반영되며 새로고침·뒤로/앞으로 가기도 지원합니다. 별도의 Vercel 경로 재작성은 필요하지 않습니다.

Supabase가 없으면 기존 데모 전시가 열리고, 관리자 주소에서는 초기 설정 안내가 표시됩니다. Supabase를 연결하면 전시관은 DB의 공개 작품만 표시합니다. **첫 연결 직후 DB가 비어 있으면 액자도 비어 있습니다.**

## 1. Supabase 프로젝트 생성

1. [Supabase Dashboard](https://supabase.com/dashboard)에 로그인하고 새 프로젝트를 만듭니다.
2. 프로젝트 이름, DB 비밀번호, 사용할 리전을 지정하고 준비가 끝날 때까지 기다립니다.
3. 프로젝트의 **Connect** 또는 **Settings → API Keys / Data API**에서 Project URL과 **Publishable key**를 확인합니다. 기존 프로젝트의 anon key도 지원합니다.

브라우저 앱에는 공개 클라이언트 키만 필요합니다. DB 비밀번호, secret key, service*role key는 `.env`의 `VITE*\*` 항목이나 프런트엔드 코드에 넣지 않습니다. [Supabase API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys)

## 2. DB와 Storage 초기 설정

Supabase **SQL Editor → New query**에서 다음 파일 내용을 각각 붙여 넣고 실행합니다.

1. [`supabase/schema.sql`](../supabase/schema.sql): 기존 방명록 조회 테이블.
2. [`supabase/artwork-management.sql`](../supabase/artwork-management.sql): 운영자 목록, 작품 테이블, 권한 함수, RLS 정책, 비공개 이미지 버킷.
3. [`supabase/room-names.sql`](../supabase/room-names.sql): 전시실 이름 테이블과 운영자 이름 수정 권한.
4. [`supabase/room-expansion.sql`](../supabase/room-expansion.sql): 전시실 추가·삭제 함수, 운영자 권한, 전시실별 액자 위치.
5. [`supabase/room-opening.sql`](../supabase/room-opening.sql): 전시실 오픈 여부와 열린 전시실의 작품·이미지 조회 정책.
6. [`supabase/youtube-artworks.sql`](../supabase/youtube-artworks.sql): 사진 또는 유튜브 영상 작품 저장.
7. [`supabase/guestbook-management.sql`](../supabase/guestbook-management.sql): 방명록 관리 함수.
8. [`supabase/account-permissions.sql`](../supabase/account-permissions.sql): 계정별 역할·담당 전시실·접근 중지.
9. [`supabase/account-deletion.sql`](../supabase/account-deletion.sql): 최고 관리자의 계정 삭제와 실패 후 재시도. 반드시 계정 권한 SQL 다음에 적용합니다.
10. [`supabase/gallery-colors.sql`](../supabase/gallery-colors.sql)로 전시실 입구·간판 글자·작품 액자 색상을 저장할 수 있게 합니다.
11. [`supabase/gallery-music.sql`](../supabase/gallery-music.sql)로 배경음악 재생 목록과 공개 재생용 음원 저장소를 만듭니다. 배경음악을 이미 설정한 프로젝트에서는 이 파일을 다시 실행하면 기존 음원이 재생 목록에 보존됩니다.

이미 작품 관리 설정을 끝낸 프로젝트는 **3·4·5·6번 파일을 순서대로 추가 실행**하면 됩니다. 기존 작품과 사진은 변경되지 않습니다.

기존 전시실과 작품 관리 설정을 마친 프로젝트에서 색상 기능을 사용하려면 앱 업데이트 전에 **10번 파일**을 실행하세요. 기존 전시실과 작품에는 현재 사용 중인 기본 색상이 적용됩니다.
입구와 액자 색상 설정을 이미 적용한 프로젝트에서도 **10번 파일**을 다시 실행하면 기존 색상을 유지하면서 간판 글자 색상 설정을 추가할 수 있습니다.

위 스크립트는 다시 실행할 수 있도록 작성했습니다. `gallery-artworks` 버킷은 private 상태로 사용하며 별도로 public으로 바꾸지 않습니다.

| 구성                 | 역할                                                      |
| -------------------- | --------------------------------------------------------- |
| `gallery_admins`     | 운영자 Auth 사용자 UUID 목록. 브라우저에서 직접 수정 불가 |
| `is_gallery_admin()` | 현재 로그인한 사용자가 운영자인지 DB에서 확인             |
| `artworks`           | 제목, 설명, 액자 위치, 사진 경로, 공개 여부, 수정 시각    |
| `gallery-artworks`   | JPEG/PNG/WebP만 허용하는 비공개 Storage 버킷              |

방문자는 공개 작품만 조회할 수 있고, DB/Storage 쓰기는 운영자만 허용됩니다. 동일한 액자 위치에는 한 작품만 등록할 수 있습니다.

공개 방명록 등록은 추가 SQL과 Edge Function 배포가 필요합니다. [방명록 연결 안내](GUESTBOOK_SETUP.md)를 참고하세요.

## 방명록 관리 연결

기존 운영자 설정이 끝난 프로젝트에서는 Supabase **SQL Editor**에서 [`supabase/guestbook-management.sql`](../supabase/guestbook-management.sql)을 추가 실행하고, 계정별 역할을 사용한다면 `account-permissions.sql`을 다시 마지막에 적용하세요. `schema.sql`과 `artwork-management.sql`이 먼저 적용되어 있어야 합니다. 기존 글은 유지되며, 방명록 등록용 Edge Function은 재배포하지 않아도 됩니다.

관리자로 로그인한 뒤 상단 **방명록 관리** 메뉴를 엽니다.

- 전체·공개·숨김 필터와 20개 단위 페이지 이동으로 글을 확인합니다.
- **숨기기**로 방문자 목록에서 제외하고 **다시 공개**로 복원합니다.
- **삭제 → 삭제하기**로 글을 영구 삭제합니다. 해당 글의 중복 요청 기록도 함께 삭제됩니다.
- **새로고침**으로 새 글이나 다른 관리자 창의 변경을 확인합니다. 방문자 화면은 방명록을 다시 열면 반영됩니다.

숨김 글 조회는 운영자 RLS 정책으로, 상태 변경·삭제는 운영자 여부를 검사하는 `moderate_guestbook` DB 함수로 처리합니다. 서버용 키를 브라우저에 추가할 필요가 없습니다. 일반 방문자와 운영자로 등록되지 않은 로그인 사용자는 관리할 수 없습니다.

SQL 적용 후 운영자 계정의 숨김·재공개·삭제, 일반 계정의 숨김 조회/관리 거부를 확인하세요. 자동 테스트는 API 요청과 실패 응답을 검증하며 실제 DB 정책 실행 검증을 대체하지 않습니다.

## 3. 첫 최고 관리자 계정 생성

첫 최고 관리자만 Supabase Dashboard에서 한 번 등록합니다. 실제 이메일은 필요하지 않습니다.

1. **Authentication → Users → Add user → Create user**에서 내부 식별 주소 `admin@accounts.gallery.invalid`와 비밀번호를 입력합니다. 이메일 확인 없이 사용 가능하도록 **Auto Confirm User**를 선택합니다.
2. `account-permissions.sql`까지 적용한 뒤 SQL Editor에서 실행합니다.

```sql
insert into public.gallery_admins (user_id,role,is_active)
select id,'owner',true from auth.users where email = 'admin@accounts.gallery.invalid'
on conflict (user_id) do nothing;
```

3. 앱에서 아이디 `admin`과 설정한 비밀번호로 로그인합니다.
4. 이후 계정은 관리 화면의 **계정·권한 관리 → 계정 추가**에서 아이디·비밀번호로 생성합니다.

내부 식별 주소는 Supabase Auth 연결용이며 메일을 발송하지 않습니다.
기존에 실제 이메일로 만든 운영자도 기존 이메일·비밀번호로 계속 로그인할 수 있습니다.
권한은 사용자 메타데이터가 아니라 `gallery_admins` 테이블로 검사합니다.

## 4. 로컬 환경변수 연결

프로젝트 루트에서 `.env.example`을 `.env`로 복사하고 다음 값을 채웁니다.

```dotenv
VITE_SUPABASE_URL=https://실제프로젝트.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=실제_publishable_key
```

기존 anon key를 사용할 경우 `VITE_SUPABASE_PUBLISHABLE_KEY` 대신 `VITE_SUPABASE_ANON_KEY`를 설정합니다. 두 키를 모두 넣으면 publishable key가 우선합니다.

개발 서버를 중단한 뒤 `npm run dev`로 다시 시작합니다. 터미널에 표시된 주소 뒤에 `/#/admin`을 붙이고, 3단계의 아이디·비밀번호로 로그인합니다. `.env`는 Git에 커밋하지 않습니다.

## 전시실 이름 변경

관리자 화면의 **전시실 관리**에서 각 전시실의 새 이름을 입력하고 **이름 저장**을 누릅니다. 공백만 있는 이름과 줄바꿈은 허용하지 않으며 최대 24자입니다. 이름이 바뀌어도 전시 위치 코드·사진·액자 배치는 유지됩니다.

변경한 이름은 전시실 입구, 미니맵, 현재 위치, 작품 상세, 전시실 필터와 위치 선택에 반영됩니다. 다른 전시관 창에서는 새로고침·창 재활성화 또는 주기적 갱신 시 반영됩니다. 이름 테이블이 아직 없거나 일시적으로 조회가 실패하면 방문자 화면은 기본 전시실 이름을 유지합니다.

관리자에서 전시관으로 돌아가면 `/`로 이동해 주소 끝의 해시가 제거됩니다.

## 전시실 추가

기존에 전시실 이름 설정까지 적용한 프로젝트는 [`supabase/room-expansion.sql`](../supabase/room-expansion.sql)을 SQL Editor에서 한 번 실행하세요. 기존 전시실과 작품은 유지됩니다. 이전 `artwork-management.sql`을 다시 실행하면 기존 액자 제한이 복원될 수 있으므로, 이 경우 `room-expansion.sql`과 `room-opening.sql`도 순서대로 다시 실행하세요.

관리자 **작품 관리 → 전시실 관리**에서 **새 전시실 이름**을 입력하고 **+ 전시실 추가**를 누릅니다. D부터 Z까지 코드를 자동 배정하며, 기존 3개를 포함해 최대 26개 전시실을 제공합니다. 이름은 줄바꿈 없이 1~24자입니다. 각 전시실에는 정면·왼쪽·오른쪽 벽에 4개씩, 총 12개의 액자가 추가됩니다.

추가 후 작품 목록의 전시실 필터와 등록 폼의 위치 선택에서 새 전시실을 선택할 수 있습니다. 로비 뒤쪽 문으로 나가면 중앙 연결 통로가 생기며, 양옆의 문을 통해 추가 전시실로 걸어갈 수 있습니다. 통로는 전시실 수에 맞게 늘어나고, 전시실이 없어지면 줄어듭니다. 마지막 추가 전시실을 삭제하면 통로가 없어지고 기존 로비 벽이 복원됩니다. 하단 **전시실 이동** 메뉴와 **로비로 이동**은 빠른 이동용으로 계속 사용할 수 있습니다.

미니맵은 기존 A/B/C·로비·연결 통로·추가 전시실과 실제 문 위치를 함께 표시합니다. 전시실을 추가하거나 삭제하면 지도도 갱신됩니다. 긴 전시관은 지도를 위아래로 스크롤해 볼 수 있으며, 방문자 위치가 보이는 범위를 벗어나면 지도가 따라갑니다.

전시실과 액자 위치는 운영자 권한을 검사하는 DB 함수에서 한 트랜잭션으로 생성합니다. 동시 추가 시 코드는 중복되지 않습니다. 액자 수 변경은 지원하지 않습니다. 자동 검증은 배치·충돌·작품 위치와 API 요청을 확인하며, 실제 DB 함수와 RLS는 SQL 적용 후 운영자/일반 계정으로 확인해야 합니다.

## 전시실 오픈 여부

전시실 추가 기능을 이미 설정한 프로젝트는 [`supabase/room-opening.sql`](../supabase/room-opening.sql)을 SQL Editor에서 한 번 실행하세요. 초기 적용 시 기존 전시실은 오픈 상태를 유지하고, 이후 추가한 전시실은 기본적으로 준비 중 상태로 생성됩니다. 스크립트를 다시 실행해도 저장된 오픈 여부는 유지됩니다. 다른 초기 설정 SQL을 다시 실행했다면 오픈 설정 SQL도 마지막에 다시 실행하세요.

관리자 **작품 관리 → 전시실 관리**에서 각 전시실의 **오픈 스위치**를 켜거나 끕니다. A/B/C와 추가 전시실 모두 설정할 수 있습니다. 준비 중인 전시실에도 작품 등록·수정·공개 설정을 할 수 있으므로 전시 준비 후 오픈하면 됩니다. 오픈 여부와 작품 공개 여부는 별개이며, 방문자에게는 오픈한 전시실의 공개 작품만 표시됩니다.

준비 중인 전시실 입구는 주름진 천과 **COMING SOON / 전시 준비 중** 표시로 가려집니다. 입구 충돌 판정으로 걸어서 들어갈 수 없으며, 전시실 이동 목록에서도 선택할 수 없습니다. 미니맵은 준비 중인 전시실을 흐린 색·점선과 준비 중 문구로 표시합니다. 연결 통로는 열려 있으므로 닫힌 전시실을 지나 다른 오픈 전시실로 갈 수 있습니다. 모든 방을 닫아도 로비와 방명록은 이용할 수 있습니다.

다른 관람 창에는 창 재활성화·주기적 갱신 또는 새로고침 시 반영됩니다. 관람 중인 방이 닫히면 로비로 돌아갑니다. 설정 조회에 실패하면 첫 화면에서 방을 임의로 오픈하지 않고 재시도 안내를 표시합니다. DB 정책도 닫힌 전시실의 공개 작품과 신규 이미지 URL 발급을 제한합니다. 이전에 발급된 서명 URL은 기존 유효기간(최대 1시간) 동안 사용 가능할 수 있습니다. 운영자는 준비 중인 전시실의 작품과 이미지를 계속 관리할 수 있습니다.

자동 테스트는 오픈 상태 저장 요청·충돌 오류, 입장 차단·재오픈·관람객 복귀, 커튼 배치를 확인합니다. 실제 DB 정책은 SQL 적용 후 운영자와 로그아웃 상태에서 각각 확인하세요.

## 추가 전시실 삭제

이전에 전시실 추가 SQL을 실행했더라도, 삭제 기능을 사용하려면 최신 [`supabase/room-expansion.sql`](../supabase/room-expansion.sql)을 다시 실행하세요. 기존 전시실과 작품은 유지됩니다.

관리자 **전시실 관리**에서 추가 전시실의 **삭제 → 삭제하기**를 누릅니다. 기본 A/B/C는 삭제할 수 없습니다. 공개·비공개를 포함한 등록 작품이 있으면 DB에서 삭제를 거부하므로 먼저 작품을 다른 전시실로 옮기거나 삭제해야 합니다. 전시실 삭제가 사진 파일이나 작품을 함께 삭제하지는 않습니다.

삭제는 전시실 정보와 빈 액자 위치를 한 트랜잭션으로 제거합니다. 다른 창에서 이름을 바꾸거나 같은 전시실을 삭제한 경우 이전 버전으로 삭제할 수 없습니다. 삭제 중 새 작품 배정을 차단하고 DB 외래 키로 작품 위치를 보호합니다. 실패 시 삭제 확인창에 안내가 표시되고 전시실 목록은 유지됩니다.

삭제 후 남은 전시실은 연결 통로 양옆으로 다시 배치되며, 전시실 코드·작품·액자 위치 코드는 유지됩니다. 방문자의 현재 전시실이 이동한 경우 그 전시실 안의 상대 위치를 유지합니다. 현재 전시실 자체가 삭제되거나 통로가 닫혀 이동할 수 없는 위치가 되면 로비로 돌아갑니다. 다른 관람 창에는 창 재활성화·주기적 갱신 또는 새로고침 시 반영됩니다.

## 5. 작품 등록

1. **새 작품**에서 전시 위치를 고릅니다. A/B/C 전시실의 정면·왼쪽·오른쪽 벽에 각각 4개 위치가 있습니다. 좌우는 로비에서 전시실로 입장하는 방향 기준입니다.
2. JPG/PNG/WebP 사진을 선택합니다. 원본 파일은 최대 10MB이며, 브라우저에서 긴 변 1,920px 이내로 조정하고 WebP로 변환해 저장합니다. WebP 출력이 지원되지 않는 브라우저는 PNG를 사용할 수 있습니다. 원본 파일은 별도로 보관하세요.
3. 제목·설명을 입력합니다. 기본은 비공개이며, **전시관에 공개**를 체크해 등록하면 오픈한 전시실에서 방문자에게 보입니다.
4. **전시관 보기**로 돌아가 확인합니다. 이미 전시관을 열고 있는 방문자에게는 새로고침 또는 창 재활성화 시 변경 사항이 반영됩니다. 등록되지 않았거나 비공개인 위치는 사진·제목 없이 빈 액자로 표시됩니다.
5. 수정할 때는 목록에서 작품을 선택합니다. 새 사진을 선택하지 않으면 기존 사진을 유지합니다. 위치 변경·제목·설명·공개 여부 수정도 가능합니다.
6. 삭제 버튼을 누르면 한 번 더 확인하고, 작품 정보 삭제 후 사용하지 않는 사진 파일을 정리합니다.

동시에 다른 창에서 수정된 작품은 덮어쓰거나 삭제하지 않고 새로고침을 안내합니다. 업로드 후 DB 저장 실패 시 새 파일을 정리합니다. 네트워크 문제로 파일 정리에 실패한 경우 Storage에 사용하지 않는 파일이 남을 수 있습니다. 다른 작품이 사용하는 파일은 삭제 정책에서 보호합니다.

이미지는 1시간 유효한 서명 URL로 전달하고, 열린 전시관에서는 만료 전에 갱신합니다. 비공개로 바꾼 뒤에도 이미 발급된 이미지 URL은 최대 1시간 유효할 수 있습니다. [Storage 접근 제어 안내](https://supabase.com/docs/guides/storage/security/access-control)

## 유튜브 영상 작품

기존 설정이 끝난 프로젝트는 [`supabase/youtube-artworks.sql`](../supabase/youtube-artworks.sql)을 SQL Editor에서 한 번 실행하세요. 기존 사진은 유지되며, 작품 하나에 사진 또는 유튜브 링크 중 하나를 저장합니다.

관리자 **작품 관리 → 새 작품 등록 → 작품 유형 → 유튜브 영상**을 선택하고 개별 영상 링크를 붙여 넣습니다. 일반 watch 링크, youtu.be 공유 링크, Shorts·라이브 영상 링크를 지원하며 재생목록은 지원하지 않습니다. 전시 위치·제목·설명·공개 여부를 설정해 저장합니다. 사진 파일 업로드는 필요하지 않습니다.

전시관에 입장하면 렌더링되는 오픈 전시실의 영상들이 거리 조건 없이 음소거로 자동 재생됩니다. 첫 관람 안내가 떠 있어도 재생되며, 방명록·작품 상세를 열면 액자 안 재생은 멈춥니다. 멀리 떨어진 전시실은 화면 성능을 위해 표시될 때 플레이어를 불러옵니다. 탭을 숨기면 재생을 일시 정지합니다. 영상 액자는 16:9 비율로 표시되며, 액자 안에서는 재생 버튼·진행 막대·키보드 조작을 비활성화합니다. 영상 화면이나 액자·작품 제목을 클릭하면 상세 창에서 더 크게 볼 수 있고, 상세 플레이어에서 일시 정지·탐색·소리 조작을 할 수 있습니다. YouTube의 영상 제목·채널 정보 등 일부 자체 표시는 공식 플레이어에서 완전히 숨길 수 없습니다.

YouTube 공식 iframe 플레이어를 사용합니다. 브라우저가 자동 재생을 막으면 영상을 클릭해 상세 창을 열고 플레이어의 재생 버튼을 눌러 주세요. 영상 소유자가 외부 재생을 막거나 영상이 삭제된 경우 YouTube에서 보기 링크를 안내합니다. 연령 제한·로그인·지역 제한 영상은 외부 재생이 제한될 수 있습니다. [YouTube 플레이어 API 안내](https://developers.google.com/youtube/iframe_api_reference)

사진 작품을 영상으로 바꾸면 저장 성공 후 이전 사진 파일을 정리합니다. 영상을 사진으로 바꿀 때는 새 사진 파일을 선택해야 합니다. 영상 작품 삭제는 저장된 링크만 삭제하며 YouTube 원본 영상은 변경하지 않습니다.

## 6. Vercel 연결

Vercel 프로젝트의 **Settings → Environment Variables**에 동일한 Project URL과 publishable key를 추가합니다. 사용할 배포 환경에 적용한 뒤 **재배포**해야 합니다. Vite의 환경변수는 빌드 시 반영됩니다.

배포 주소에 `/#/admin`을 붙여 로그인하고 사진을 관리하면, 작품 변경은 Supabase에 저장되므로 사진이나 전시실 이름을 바꿀 때마다 소스를 재배포할 필요는 없습니다.

## 연결 후 확인할 동작

Supabase 프로젝트가 아직 없어 실서비스 Auth/DB/Storage 연동은 실행하지 못했습니다. 최초 설정 후 다음을 확인하세요.

- 로그아웃 상태의 시크릿 창: 공개 작품만 보이고 비공개 작품은 조회되지 않는지
- 운영자 목록에 없는 계정: 로그인해도 관리 화면 접근이 거절되는지
- 운영자: 사진 업로드, 공개 전환, 제목·설명·사진 교체, 위치 변경, 삭제가 되는지
- 같은 위치에 두 번 등록: 중복 오류로 차단되는지
- 두 관리자 창에서 같은 작품 수정: 이전 버전으로 저장한 쪽이 충돌 안내를 받는지
- 로그아웃 또는 권한 회수 후 DB/Storage 쓰기가 거절되는지

자동 검증은 이미지·메타데이터 검사, API 요청·실패 복구, 로그인 후 역할 확인·로그아웃 경쟁 상태를 포함합니다. API 테스트는 네트워크 응답을 대체하며 실제 Supabase RLS 실행 검증은 아닙니다.

## 이번 작업에 포함되지 않은 것

공개 회원가입·비밀번호 재설정·MFA, 원본 사진 보관은 별도 구현 대상입니다. 최고 관리자가 앱에서 아이디·비밀번호로 계정을 생성할 수 있습니다. 공개 방명록 등록용 Edge Function은 구현되어 있으며 별도 설정 안내에 따라 배포해야 합니다. 운영자 비밀번호 관리는 현재 Supabase Dashboard에서 수행합니다.

## 계정별 역할·담당 전시실 설정

기존 설정과 `guestbook-management.sql`을 적용한 다음, **마지막으로**
[`supabase/account-permissions.sql`](../supabase/account-permissions.sql)을 실행한 뒤
[`supabase/account-deletion.sql`](../supabase/account-deletion.sql)을 적용하세요.
이전부터 `gallery_admins`에 있던 운영자는 최초 적용 시 최고 관리자로 유지됩니다.
새 역할은 로그인 계정의 DB 레코드로 판단하며 사용자 메타데이터를 신뢰하지 않습니다.

| 기능                                      | 최고 관리자 | 전시 관리자          | 작품 편집자 |
| ----------------------------------------- | ----------- | -------------------- | ----------- |
| 계정 추가·삭제·권한 변경·접근 중지        | 전체        | 불가                 | 불가        |
| 전시실 이름·오픈 설정·빈 추가 전시실 삭제 | 전체        | 담당 전시실          | 불가        |
| 전시실 추가                               | 가능        | 전체 전시실 담당자만 | 불가        |
| 작품 등록·내용·사진·영상 수정             | 전체        | 담당 전시실          | 담당 전시실 |
| 기존 작품 공개 전환·배치 변경·삭제        | 전체        | 담당 전시실          | 불가        |
| 방명록 관리·숨김 글 조회                  | 가능        | 불가                 | 불가        |

작품 편집자는 새 작품을 비공개로 등록하고, 등록 시 첫 위치를 선택합니다.
기존 작품의 공개 여부와 위치는 변경할 수 없습니다. 이미 공개된 작품의 제목·설명·사진·영상 수정은 즉시 공개 내용에 반영됩니다.
최고 관리자는 모든 전시실을 관리합니다. 다른 역할은 전체 전시실 또는 일부 전시실을 지정하며,
담당 전시실을 하나도 고르지 않으면 작품·전시실 관리 권한이 없습니다.
전체 전시실 담당자는 나중에 추가한 전시실도 담당합니다. 전시실을 삭제하면 해당 전시실의 개별 담당 배정도 해제합니다. 같은 코드로 새 전시실을 만들어도 이전 담당자에게 자동 배정되지 않습니다.

최초 설정 시 운영자 계정이 아직 없다면 위 **첫 최고 관리자 계정 생성** 절차를 따르세요.
이후 `/#/admin/accounts`의 **계정·권한 관리**에서 계정을 추가하거나 권한을 수정합니다.
접근 중지는 Auth 계정을 삭제하지 않고 관리 기능을 차단합니다.
마지막 활성 최고 관리자의 권한 축소·접근 중지는 DB 함수에서 거부합니다.

DB/Storage는 매 요청에 현재 권한을 검사합니다. 열린 관리 화면도 창 재활성화 및 1분 간격으로 권한을 갱신합니다.
기발급 이미지 서명 URL은 기존 최대 1시간의 유효기간이 남을 수 있습니다.
다른 사람이 올린 사진을 교체·삭제한 경우 작품 변경은 적용되지만 파일 정리 권한에 따라 안내가 표시될 수 있으며,
최고 관리자가 Storage에서 사용하지 않는 파일을 정리할 수 있습니다.
기존 초기 설정 SQL을 다시 실행했다면 이 권한 SQL과 계정 삭제 SQL을 **이 순서로 다시 마지막에 실행**하세요. 이전 SQL은 넓은 운영자 권한을 복원할 수 있습니다.

### 앱에서 아이디·비밀번호로 계정 추가

최고 관리자가 **계정 추가**에서 다음을 입력합니다.

- 아이디: 영문·숫자·밑줄·하이픈 3~32자. 대소문자는 구분하지 않습니다.
- 비밀번호와 확인: 8~72자. 프로젝트의 추가 비밀번호 정책도 적용됩니다.
- 역할, 담당 전시실, 활성 여부.

저장하면 설정한 아이디와 비밀번호로 바로 로그인할 수 있습니다.
실제 이메일·메일 수신함·초대 메일·이메일 인증·SMTP·초대 리다이렉트 설정은 필요하지 않습니다.
아이디는 생성 후 변경하지 않으며 기존 계정 편집은 역할·담당 범위·상태를 변경합니다.
비밀번호는 생성 시에만 입력하고 화면에 저장·표시하지 않습니다.
사용자에게 아이디와 비밀번호를 전달하는 작업은 운영자가 직접 수행합니다.

계정 생성용 서버 함수를 한 번 배포하세요.

```bash
supabase functions deploy admin-create-account
supabase secrets set ADMIN_ALLOWED_ORIGINS=https://실제전시관주소
```

로컬 테스트 주소도 필요하면 쉼표로 추가합니다(예: `http://localhost:5173`).
허용 주소는 경로와 끝 슬래시 없는 origin입니다.
함수는 서버 환경의 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`를 사용합니다.
서비스 키를 `VITE_*` 환경변수나 브라우저에 추가하지 않습니다.
Supabase Auth의 공개 신규 가입은 비활성화하고 관리자 생성 API로만 계정을 만드세요.

구현은 아이디를 `아이디@accounts.gallery.invalid`라는 내부 Auth 식별자로 변환합니다.
서버의 `auth.admin.createUser`에 비밀번호와 `email_confirm: true`를 전달하며 메일을 보내지 않습니다.
중복 아이디는 거부하고 기존 계정의 비밀번호나 권한을 덮어쓰지 않습니다.
DB 권한은 호출자의 현재 최고 관리자 권한을 다시 검사하여 등록합니다.
등록 실패 시 이번 요청으로 만든, 아직 권한이 없는 Auth 계정만 정리합니다.

이전 초대 구현의 `admin-invite`를 이미 배포했다면 해당 함수를 제거하세요.
계정 생성에는 `admin-create-account`만 사용합니다.

### 최고 관리자의 계정 삭제

계정 삭제 기능을 추가로 적용하려면 SQL Editor에서
[`supabase/account-deletion.sql`](../supabase/account-deletion.sql)을 실행한 뒤 아래 함수를 배포하세요.
기존 `ADMIN_ALLOWED_ORIGINS` 설정을 그대로 사용합니다.

```bash
npx supabase functions deploy admin-delete-account --project-ref 프로젝트ID
```

**계정·권한 관리 → 계정 선택 → 이 계정 삭제 → 삭제하기**로 삭제합니다.
확인창에는 계정 아이디와 복구 불가 안내가 표시됩니다. 취소하면 삭제하지 않습니다.
현재 로그인한 계정과 마지막 활성 최고 관리자 계정은 서버에서 삭제를 거부합니다.
삭제 요청의 계정 버전도 검사하므로, 다른 창에서 권한을 바꾼 계정을 이전 정보로 삭제할 수 없습니다.

삭제를 시작하면 먼저 DB 관리 권한을 차단하고, 서버에서 Auth 계정을 삭제한 다음 운영 계정 목록에서 제거합니다.
Auth는 작품 작성자 UUID와 Storage 파일 참조를 보존하는 soft delete를 사용합니다.
기존 로그인 자격과 세션을 제거하며 등록 작품·사진·전시실·방명록은 삭제하지 않습니다.
동작 근거는 [Supabase deleteUser 문서](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)를 참고하세요.

중간에 통신이나 서버 처리가 실패하면 **삭제 진행 중 · 다시 시도 필요**로 표시합니다.
이 계정은 관리 권한을 복구하거나 다른 역할로 변경할 수 없고, **계정 삭제 다시 시도**로 삭제를 완료할 수 있습니다.
다시 시도할 때 이미 삭제된 Auth 계정에 대한 soft delete는 재실행 가능합니다.
브라우저에는 서버용 키를 제공하지 않고, 삭제 확정 DB 함수는 `service_role`에만 허용합니다.

### 이전 계정 변경 로그 제거 적용

계정 변경 로그 화면과 저장·조회 기능은 제거했습니다.
이미 이전 SQL을 적용한 프로젝트는 `account-permissions.sql` → `account-deletion.sql` 순서로 다시 실행하세요.
계정 권한·삭제 함수에서 로그 저장을 제거한 뒤, 기존 로그 조회 함수와 로그 테이블·데이터를 정리합니다.
삭제 재시도에 필요한 진행 상태와 계정 아이디만 유지합니다. 서버 함수 재배포는 필요하지 않습니다.

### 적용 후 확인

자동 테스트는 세션 전환·접근 중지·담당 범위와 계정 생성 핸들러의 권한 거부·중복 아이디·입력 검사·실패 정리를 확인합니다.
실제 Supabase 정책과 계정 생성·로그인 검증은 SQL·함수 배포 후 아래 계정으로 진행하세요.

- 최고 관리자: 계정 목록·방명록 조회 및 계정 권한 변경·삭제. 마지막 최고 관리자 접근 중지·삭제와 자기 계정 삭제 거부.
- 계정 삭제: 취소 시 유지, 확인 시 로그인 불가와 목록 제거. 작품·사진 유지. 중간 실패 후 삭제 재시도.
- B 전시실 담당 전시 관리자: B 작품·전시실 관리 가능. A/C 비공개 작품 접근·수정 및 방명록 관리 거부.
- B 전시실 작품 편집자: 비공개 등록과 내용 수정 가능. 공개 전환·기존 배치 변경·작품 삭제·전시실 설정 거부.
- 접근 중지 계정: DB/Storage 쓰기와 숨김·비공개 자료 조회 거부. 공개 관람은 일반 방문자와 동일.
- 새 계정: 아이디·비밀번호·역할 지정 → 저장 → 로그아웃 → 새 아이디·비밀번호로 로그인. 잘못된 비밀번호와 중복 아이디는 거부되는지 확인.
- 두 관리자 창에서 같은 계정 수정: 이전 버전 저장 거부. 다른 계정 권한으로 빠르게 전환해도 이전 권한이 유지되지 않는지 확인.
